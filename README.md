# 업무 리듬 봇 (worklife-bot)

퇴직했거나 혼자 일하게 된 사람이 **직장에 다닐 때의 리듬을 그대로 유지**하도록 돕는 슬랙 앱.

직장의 리듬은 사실 네 가지뿐이다. 이 앱은 그 네 개를 슬랙 안에 다시 만든다.

| 직장에서 | 이 앱에서 |
|---|---|
| 출근해서 오늘 할 일을 정한다 | 아침 리마인드 → `/checkin`, `/출근` |
| 하루 종일 일하고 기록한다 | `/done`, 홈 탭 체크리스트 |
| 퇴근 전 일일보고를 쓴다 | **저녁 done-next 대화 (핵심)** |
| 주간회의·분기 목표를 챙긴다 | 주간보고 자동 발송, 마일스톤 진행도 |

---

## 하루 흐름

```
09:00  봇 → "좋은 아침입니다."
             :sunrise: 오늘의 모닝 루틴
             1. DM 에 아카이빙해 둔 자료 확인하기
             2. 오늘 할 일 정하기
             3. /출근 찍고 시작하기
             ─────
             어제 한 일 · 오늘 하기로 한 일 · 안 끝난 할 일
             💬 어제 나에게 한 말 · 🎯 마일스톤 진행도       [출근하기] [할 일 정하기]
       나 → /출근
 ...
17:50  봇 → "안녕하세요, ○○님! Daily Retro & Planning 시간이에요."
       봇 → "1️⃣ '오늘' 어떤 작업을 하셨나요?"
             In your previous report, you mentioned:
             • 어제 NEXT 로 적었던 것들
       나 → (자유롭게 작성)
       봇 → "2️⃣ '내일' 어떤 작업을 계획하고 계신가요?"
       나 → (자유롭게 작성)   ← 이 줄들이 내일 할 일로 자동 등록된다
       봇 → "3️⃣ 오늘 하루도 고생한 나에게 해주고 싶은 말은?"
       나 → (자유롭게 작성)
       봇 → "🎉 Daily Retro/Planning 응답이 완료되었습니다!"
             🔥 연속 12일째 · 오늘 근무 8시간 30분 · 채널에 공유했습니다
18:40  (아직 안 냈으면) 봇 → 넛지 1회
금 17:00  주간보고 자동 생성 → DM + 공개 보드 채널
```

핵심은 **어제 하기로 한 일을 오늘 다시 보여 준다**는 것이다.
빈 화면에서 기억을 짜내는 것과, 목록을 보고 고치는 것은 전혀 다른 일이다.

### 입력은 0hop, 취합은 1hop

이 앱의 UI 원칙이다.

- **내가 입력한 것은 입력한 그 자리에서 그대로 다시 보여야 한다 (0hop).**
  그래서 할 일 등록도, done-next 도 **모달을 쓰지 않는다.** 봇이 DM 으로 묻고,
  사용자가 평범한 메시지로 답하고, 봇이 저장 내용을 되읽어 준다.
  질문·답변·확인이 전부 대화에 쌓여서 위로 스크롤만 하면 다시 보인다.
- **여러 날·여러 항목을 모아 보는 것은 별도 뷰여도 된다 (1hop).**
  `/plan` `/report` `/milestone` `/settings` 처럼 명령으로 여는 화면이 여기 해당한다.

임시(ephemeral) 응답과 `response_url` 응답도 같은 이유로 피한다 —
전자는 새로고침하면 사라지고, 후자는 **원본 메시지를 교체**해 버린다.

## 명령어

| 명령 | 하는 일 |
|---|---|
| `/출근` `/퇴근` | 근무 시작·종료. ASCII 로 `/in` `/out` 도 됨. DM 에 그냥 `출근` 이라고 적어도 동작 |
| `/근무` (`/hours`) | 오늘·이번주·이번달 근무시간. `/근무 수정 09:30 18:00` 로 정정 |
| `/standup` | done-next 대화를 지금 시작. `/standup 다시` 로 재작성 |
| `/checkin` | 오늘 할 일 정하기 — **DM 대화**로 묻고 답을 받는다 |
| `/done <내용>` | 방금 끝낸 일을 바로 완료로 기록 |
| `/plan` | 오늘 할 일 목록 + 체크·미루기·삭제 |
| `/milestone` | 목록. `new` 로 생성, `progress <번호> <%>`, `done <번호>` |
| `/report [기간] [공유\|파일]` | 붙여넣기용 업무보고. 기간은 아래 참고 |
| `/history [기간] [파일]` | 날짜별 한 줄 요약 — 얼마나 꾸준했는지 훑어보기 |
| `/streak` | 연속 기록 |
| `/pause <일수\|날짜\|해제>` | 휴가. 그동안 안 묻고 **연속 기록도 안 끊긴다** |
| `/settings` | 타임존·근무요일·알림 시각·공개 보드 채널 |
| `/help` | 사용법 |

### 아침 리마인드 (09:00)

두 부분이다. **모닝 루틴 알람** + **어제 기록 되짚기**.

```
:sunrise: 오늘의 모닝 루틴
1. DM 에 아카이빙해 둔 자료 확인하기
2. 오늘 할 일 정하기
3. /출근 찍고 시작하기
```

루틴 항목은 `src/slack/copy.ts` 의 `COPY.morning.routine` 배열 하나로 바꾼다.
봇이 DM 내용을 대신 읽어 주지는 않는다 — **알람 역할까지만** 한다.
출근 시각이 유연해도 되도록 별도 알람을 두지 않고 이 한 통에 합쳤다.

그 아래에 어제 이 봇 DM 에 남긴 기록을 붙인다.

| 담기는 것 | 어디서 왔나 |
|---|---|
| 어제 한 일 | done-next Q1 |
| 하기로 하신 일 | done-next Q2 → 오늘 할 일로 자동 등록된 것 |
| 아직 안 끝난 할 일 | 이월된 계획 |
| 💬 어제 나에게 한 말 | done-next Q3 |
| 🎯 마일스톤 진행도 | 진행 중인 것 최대 3개 |

여기서 "아카이브" 는 self-DM("나에게 보낸 메시지")이 아니라 **이 봇과의 DM 에 쌓인 기록**이다.
self-DM 은 봇 토큰으로 읽을 수 없다.

### 근무시간 계산

기본 정책은 **월~금 09:30~18:00, 점심 12:30~14:00 → 실 근무 7시간**.

점심은 길이가 아니라 **시각 구간**이다 (`LUNCH_START`, `LUNCH_END`).
근무 구간과 겹치는 만큼만 뺀다.

| 근무 | 겹치는 점심 | 실 근무 |
|---|---|---|
| 09:30 ~ 18:00 | 90분 | 7시간 |
| 09:30 ~ 13:00 | 30분 | 3시간 |
| 09:30 ~ 12:00 | 0분 | 2시간 30분 |
| 14:00 ~ 18:00 | 0분 | 4시간 |

오전 반차인 날에 1시간 30분을 빼면 안 되니까 이렇게 한다.

기록이 없을 때의 기본값.

| 상황 | 기록되는 근무시간 |
|---|---|
| 출근을 안 찍었다 | **0시간** — 없는 날은 없는 날이다 |
| 출근만 찍고 퇴근을 안 찍었다 | **정규 퇴근 18:00 으로 마감** → 7시간 (`DEFAULT_CLOCK_OUT`) |

모르는 값을 크게 잡으면 통계가 통째로 망가진다. 정규 근무일로 두고,
다르면 `/근무 수정 2026-09-16 09:30 18:00` 로 고친다. 자정을 넘긴 근무도 알아서 처리한다.

### 기간 지정

`/report` 와 `/history` 가 같은 문법을 쓴다.

| 입력 | 구간 |
|---|---|
| (없음) | 오늘 |
| `주간` `월간` | 이번 주 / 이번 달 |
| `지난주` `지난달` | 저번 주 / 저번 달 |
| `2026-09-05` | 그 하루 |
| `2026-08` | 그 달 |
| `2026-09-01~2026-09-10` | 임의 구간 (뒤집어 써도 정렬한다) |
| `30일` | 최근 30일 |

뒤에 `공유` 를 붙이면 보드 채널에, `파일` 을 붙이면 마크다운 파일로 DM 에 보낸다.
슬랙 메시지는 블록당 3000자라 몇 주치가 넘어가면 잘리므로, 긴 기간은 파일이 낫다.
파일 전송에는 `files:write` 권한이 필요하다 (manifest 에 들어 있다).

### 답변을 할 일로 쪼개는 규칙

NEXT 답변은 다음 근무일의 할 일이 된다. 쪼개는 기준은 `src/domain/textItems.ts` 한 곳에 있다.

- 자른다 — 줄바꿈, 줄 앞의 `-` `•` `1.` `①` `✅`, 한 줄 안의 ` / ` ` ; ` ` | ` ` • `, 중간에 다시 나오는 `2.`
- **자르지 않는다 — 쉼표.** 한국어에서 쉼표는 항목 구분보다 문장 안 쉼표로 훨씬 자주 쓰인다
  ("웹훅 ERD + PRD 작성, 영상님과 미팅 (~70%)" 은 두 개가 아니라 한 항목이다)
- `2.5시간 공부` 의 `2.` 는 목록 번호가 아니다 (숫자 기호는 뒤에 공백이 있을 때만 인정)
- URL 안의 `/` 는 붙어 있어 걸리지 않는다
- `없음` `해당 없음` 같은 답은 할 일로 만들지 않는다

원문은 손대지 않고 그대로 저장된다. 이 규칙은 표시와 할 일 생성에만 쓴다.

### 연속 기록(streak)

**근무일 기준**이다. 주말과 `/pause` 로 잡아 둔 휴가는 건너뛴다.
쉬는 날 때문에 기록이 끊기면 쉬는 게 벌이 되고, 그건 이 앱의 취지와 반대다.

### 두 채널로 나뉜다

**개인 DM 과 공개 채널이 하는 일이 다르다.**

| | DM (봇과의 1:1) | 공개 보드 채널 |
|---|---|---|
| 아침 리마인드 (모닝 루틴 + 어제 기록) | ✅ | |
| done-next 질문·답변 | ✅ 세 질문 전부 | |
| `/done` `/plan` `/근무` 등 개인 기록 | ✅ | |
| 하루 시작 알림 | | ✅ "Daily Retro & Planning 시간입니다" |
| **개인별 DONE/NEXT 요약** | | ✅ 각자 3번 질문까지 마치면 올라간다 |
| 마감 현황 | | ✅ 낸 사람만 호명 (안 낸 사람 이름은 안 부른다) |
| 주간보고 | ✅ | ✅ |

질문과 답변은 **DM 에서만** 오간다. 봇은 DM(`message.im`) 밖의 메시지를 답변으로 받지 않는다.
채널에는 신호와 결과만 올라간다.

보드 채널은 `BOARD_CHANNEL_ID` 로 못 박는다. 안 정하면 봇이 들어가 있는 채널 중 하나를
자동으로 고르는데, 채널이 둘 이상이면 어느 쪽이 잡힐지 단정할 수 없다.
채널 id 는 `npm run channels` 로 확인한다.

봇이 초대된 채널이 곧 참여자 명단이다. 별도 명단 관리가 없다.
개인별 공유는 `/settings` 에서 끌 수 있다. 남이 본다는 감각이 출근의 절반이다.

## 적용하기

### 1. 슬랙 앱 만들기 (5분)

1. <https://api.slack.com/apps> → **Create New App** → **From an app manifest**
2. 워크스페이스를 고르고, 이 저장소의 `manifest.json` 내용을 그대로 붙여넣기
3. **Basic Information → App-Level Tokens → Generate Token and Scopes**
   - 이름 아무거나, 스코프는 **`connections:write`** 하나
   - 나온 `xapp-...` 토큰을 복사해 둔다 → `SLACK_APP_TOKEN`
4. **Install App → Install to Workspace** → 나온 `xoxb-...` 복사 → `SLACK_BOT_TOKEN`
5. 요약을 올릴 공개 채널에 봇을 초대한다: 그 채널에서 `/invite @<봇 이름>`

> 한글 슬래시 명령(`/출근`)을 슬랙이 거절하면, manifest 에서 그 세 줄을 지우고
> `/in` `/out` `/hours` 만 쓰면 된다. DM 에 `출근` 이라고 적는 방법은 항상 동작한다.

### 2. 로컬에서 확인

```bash
cp .env.example .env      # SLACK_BOT_TOKEN, SLACK_APP_TOKEN 채우기
npm install
npm run smoke             # 슬랙 없이 계산 로직만 검증
npm run dev               # 실제 연결
```

떴으면 슬랙에서 봇에게 DM 으로 `도움말` 이라고 적어 본다.
`/standup` 을 치면 시간과 상관없이 done-next 대화가 바로 시작된다.

### 3. Railway 에 올리기

```bash
git init && git add -A && git commit -m "업무 리듬 봇"
# GitHub 에 올린 뒤 Railway → New Project → Deploy from GitHub repo
```

🔴 **볼륨을 붙이는 것만으로는 부족하다. `DATABASE_PATH` 를 그 마운트 경로로 지정해야 한다.**

기본값은 `./data/worklife.sqlite` 라서, 볼륨을 `/data` 에 붙여 놓고 이 변수를 안 넣으면
컨테이너 안 `/app/data/` 에 쌓인다. 볼륨과 전혀 다른 곳이고 재배포하면 통째로 사라진다.
실제로 그렇게 하루치 데이터를 잃은 적이 있다.

부팅 로그가 어느 쪽인지 알려 준다.

```
SQLite 열림: /data/worklife.sqlite · 기존 파일 이어서 씀 · 110592바이트
저장된 행: users=2 tasks=7 standups=3 attendance=2 job_runs=5
```

`새로 만듦` 이라고 나오거나 행이 전부 0 이면 볼륨을 못 쓰고 있는 것이다.
상대경로면 경고도 같이 뜬다.

1. Railway 프로젝트 → 서비스 → **Variables** 에 환경변수 입력

   | 키 | 값 |
   |---|---|
   | `SLACK_BOT_TOKEN` | `xoxb-...` |
   | `SLACK_APP_TOKEN` | `xapp-...` |
   | `SLACK_MODE` | `socket` |
   | `DATABASE_PATH` | `/data/worklife.sqlite` |
   | `BOARD_CHANNEL_ID` | 요약을 올릴 채널 id (`npm run channels` 로 확인) |
   | `DEFAULT_TZ` | `Asia/Seoul` |
   | `LUNCH_START` / `LUNCH_END` | `12:30` / `14:00` |
   | `DEFAULT_CLOCK_OUT` | `18:00` |

2. 서비스 → **Settings → Volumes → Add Volume**, 마운트 경로 **`/data`**
3. 배포. 로그에 `Socket Mode 로 슬랙에 연결했습니다.` 가 뜨면 끝

> 🔴 **Node 버전을 22 로 고정해 뒀다.** `.nvmrc` 와 `package.json` 의 `engines.node` 둘 다.
> `better-sqlite3` 는 네이티브 모듈이고 **Node 24 용 prebuilt 바이너리가 없다.**
> 버전을 범위(`>=20`)로 두면 Nixpacks 가 최신을 골라 소스 컴파일로 넘어가는데,
> Nixpacks 이미지에 Python 이 없어서 빌드가 죽는다. 올리기 전에 확인하는 법:
>
> ```bash
> curl -s https://api.github.com/repos/WiseLibs/better-sqlite3/releases/tags/v11.10.0 \
>   | grep -o 'node-v[0-9]*-linux-x64'
> ```
>
> Node 22 = ABI 127, Node 20 = 115, Node 24 = 137. 목록에 있는 것만 쓴다.

> 빌드 명령이 `npm ci` 가 아니라 **`npm install --include=dev`** 인 이유가 둘 있다.
>
> - `npm ci` 는 `node_modules` 를 통째로 지운다. Nixpacks 는 `node_modules/.cache` 에
>   빌드 캐시를 **마운트**해 두므로 그걸 rmdir 하려다 `EBUSY` 로 죽는다.
>   `npm install` 은 있는 것을 두고 모자란 것만 채워서 마운트를 안 건드린다.
> - Railway 가 production 모드로 설치하면 `typescript` 가 빠져 `tsc` 가 없다.
>   `--include=dev` 로 강제한다.
>
> Nixpacks 는 install 단계에서 이미 의존성을 깔아 두므로 이 명령은 보통 금방 끝난다.

Socket Mode 라서 공개 URL·도메인·서명 검증이 전혀 필요 없다.
HTTP 로 받고 싶으면 `SLACK_MODE=http` + `SLACK_SIGNING_SECRET` 을 넣고,
슬랙 앱 설정에서 Socket Mode 를 끈 뒤 Request URL 을 `https://<도메인>/slack/events` 로 지정한다.

### 4. 첫 설정

1. 봇 DM 의 **홈** 탭을 연다 → 오늘 현황이 보인다
2. `/settings` 로 타임존·근무요일·아침/저녁 시각·공개 보드 채널을 정한다
3. 끝. 내일 아침부터 알아서 말을 건다

## 백업

기록 전부가 SQLite 파일 하나(`DATABASE_PATH`)에 들어 있다.

```bash
# Railway CLI 로 내려받기
railway run cat /data/worklife.sqlite > backup-$(date +%F).sqlite
```

## 구조

```
src/
  config.ts            환경변수 로딩·검증 (부팅 때 형식 오류를 잡는다)
  db/                  SQLite. schema.ts 가 유일한 진실
  domain/              슬랙을 모르는 순수 로직 — 연속기록·근무시간·마일스톤·보고서
  slack/               Block Kit, 명령·액션·모달·이벤트 핸들러
    copy.ts            봇이 하는 말 전부. 말투를 바꾸려면 여기만 고친다
  service/             도메인과 슬랙을 잇는 흐름 (done-next 대화 상태기계 등)
  scheduler/           1분마다 돌며 사용자 타임존 기준으로 알림을 쏜다
scripts/smoke.ts       슬랙 없이 도메인 로직 검증 (action_id 중복 검사 포함)
scripts/list-channels.ts  봇이 들어가 있는 채널 id 확인
scripts/verify-home.ts    홈 탭 블록이 슬랙에서 통과하는지 확인
```

설계에서 신경 쓴 것 두 가지.

- **알림 중복 방지** — `job_runs` 테이블에 `(사용자, 잡, 날짜)` 를 원자적으로 INSERT 한다.
  Railway 가 재배포로 프로세스를 다시 띄워도 그날 알림이 두 번 가지 않는다.
  프로세스가 잠깐 죽어 있었으면 2시간 안에서는 늦게라도 보낸다.
- **날짜는 문자열** — 사용자 타임존 기준 `YYYY-MM-DD` 로만 다룬다.
  Date 객체를 들고 다니면 UTC 자정 경계에서 하루가 밀린다.
